# 푸리 (Puri)

Android 태블릿에서 문제집 PDF에 펜 필기하고, 객관식을 기하 판정으로 자동 채점하는 로컬 전용 앱.
**서버 없음 · 외부 통신 없음 · AI 호출 없음.** 상세 설계는 [`docs/푸리_1차MVP_아키텍처명세서.md`](docs/푸리_1차MVP_아키텍처명세서.md) 참조.

## 구조

Turborepo + pnpm 모노레포. 앱은 `apps/student-mobile` 하나다.

## 디자인 시스템

가이드는 [`docs/design-system/README.md`](docs/design-system/README.md) — 톤은 "담담한 도구",
색은 장식이 아니라 진단(O 그린 / △ 앰버 / X 레드, 원인 태그 5색), 이모지·그라데이션·색 보더 액센트 금지.
폰트는 오프라인 앱 특성상 CDN 대신 npm 번들(Pretendard Variable, JetBrains Mono)로 교체했다.
`pnpm dev` 후 문서 목록의 **디자인 시스템** 버튼(dev 전용)에서 전 컴포넌트 갤러리를 볼 수 있다.

### 분할 알고리즘 비교

두 분할기(`segment.ts` v1 / `psp/` v2)를 같은 PDF에 돌려 나란히 본다.

- **화면** — `pnpm dev` 후 노트 목록 사이드바의 **분할 비교** 버튼(dev 전용).
  PDF를 열면 페이지 원본 위에 양쪽 결과를 나란히 그리고, 신뢰도별 색(녹/황/적)과
  선지 판정 박스(hitbox)를 겹쳐 보여준다. 갈린 지점은 칩으로 나열되어 클릭하면 이동한다.
- **수치** — 실제 PDF는 저작물이라 리포에 넣지 않는다. 경로를 넘겨 헤드리스로 돌린다:

  ```sh
  PURI_BENCH_PDF=~/Downloads/문제집.pdf npx vitest run bench.real
  ```

  경로가 없으면 그냥 건너뛴다. 커버리지 분모는 양쪽 모두 PSP가 산출한 본문 영역을 쓴다 —
  페이지 텍스트 전체 범위로 재면 머리말·꼬리말을 제대로 걷어내는 쪽이 손해를 보기 때문이다.

### 골든셋

위 지표는 골든 라벨이 없어 **두 알고리즘이 얼마나 다른가**만 잰다. 어느 쪽이 옳은지는
사람이 정한 정답 구역이 있어야 말할 수 있다 (명세 준비도 #14).

`pnpm dev` → 사이드바 **골든셋 라벨링**(dev 전용)에서 만든다.

1. PDF를 열면 PSP 결과가 초안으로 깔린다. 빈 화면에서 그리지 않는다 — 고치는 편이 훨씬 빠르다.
2. 페이지마다 구역을 손보고 `Enter`로 **확인 완료 + 다음 페이지**.
   - 빈 곳 드래그 = 새 구역, 모서리 드래그 = 크기 조정, `Del` = 삭제, `F` = PSP로 채우기, `C` = 선지 편집
   - **구역 0개인 채로 확인 완료 = "문항 없음이 정답"**. 표지·목차·개념 설명 페이지가 여기 해당한다.
     이 구분이 없으면 미검출과 정상 동작을 구별할 수 없다.
   - 확인하지 않은 페이지는 채점에서 통째로 빠진다.
3. 작업은 브라우저에 자동 저장된다. 끝나면 **JSON 내보내기**.

채점은 두 곳에서 볼 수 있다.

- **분할 비교** 화면 — 같은 파일명의 골든셋을 자동으로 물고 두 알고리즘을 나란히 채점한다.
  놓친 구역·잘못 만든 구역은 칩으로 나열되고 클릭하면 그 페이지로 이동한다.
- CLI:

  ```sh
  PURI_BENCH_PDF=~/Downloads/문제집.pdf PURI_GOLDEN=~/golden-문제집.json npx vitest run bench.real
  ```

지표는 IoU 0.7 기준 재현율(= 명세의 L1 경계 정확도), 정밀도, F1, 평균 IoU, 번호 정확도,
선지 전량 검출률이다. 선지를 라벨링하지 않은 문항은 선지 점수에서 빠진다.

웹 dev 모드 제약: PDF 원본은 네이티브에서만 Filesystem에 저장된다. 브라우저에서는
메모리 캐시라서 **새로고침하면 문서를 다시 가져와야 한다.**

## 라이브 노트

채점 버튼 없이, 필기하는 동안 고른 번호를 읽어 문제 번호 위에 띄우는 화면이다.
문제집 PDF를 열고 그 위에 그대로 필기하면 된다. 텍스트 PDF는 글자를, 스캔본은 이미지를 본다.

1. **펜이 페이지에 닿으면** 그 쪽 분석이 시작된다 (탭도 접촉이다). 업로드 시점에는
   아무것도 나누지 않는다.
2. 문제 번호와, 객관식이면 ①~⑤ 체크 자리(hitbox)를 문항에 연결해 둔다.
3. 그 자리에 동그라미·체크·빗금을 치면 어느 번호인지 바로 읽는다. 고쳐 치면 마지막이 이긴다.
4. 문제 번호 위에 `12번 · 내 답 ③`으로 띄운다 — **무엇을 문제 번호로 봤는지**까지 함께
   보여준다. 번호를 잘못 잡으면 답도 엉뚱한 문항에 붙기 때문이다. 번호로 인식한 자리에는
   점선 테두리가 같이 뜬다. 스캔본은 번호 값을 읽지 않으므로 그 자리를 잘라낸 그림을 띄운다
   (`[0109] · 내 답 ③`).

### 텍스트 PDF — 문서를 통독한다

분석 단위는 페이지지만 **읽는 단위는 문서**다. 첫 접촉 때 파일 전체를 한 번 훑고,
그 결과에서 해당 페이지 몫을 꺼낸다. PSP의 판단 근거 절반이 문서 전체 통계이기
때문이다 — 실측(수능 20p)에서 앞뒤 2쪽만 보고 자르면 20쪽 중 13쪽이 전체 통독과
달랐다. 쪽번호가 문항 번호로 잡히고, 그 가짜 앵커가 앞 문항을 잘라 선지를 통째로 잃는다.
통독 비용은 쪽당 6ms 남짓이고 페이지마다 await로 끊기므로 그리는 획을 막지 않는다.

### 스캔본 — 픽셀에서 찾는다 (OCR 없음)

텍스트 레이어가 없으면(복합기로 뜬 스캔본) 페이지를 1700px 폭으로 렌더해 이미지에서 직접 찾는다.
글자는 읽지 않는다. 조판이 남긴 기하 신호만 쓴다:

| 찾는 것 | 신호 | 실측 (600dpi 스캔 → 1700px) |
|---|---|---|
| 선지 마커 ①~⑤ | 정사각 링 — 테두리만 잉크라 채움률이 낮고 속이 뚫렸다 | 27×27px, 채움 0.13~0.15, 구멍 0.55~0.62 |
| 한글 고리 ㅇ·ㅁ (제외 대상) | 같은 링이지만 작고 두껍다 | 채움 ≥0.22, 구멍 ≤0.47 |
| 문제 번호 | **종이 위의 유채색 글자 덩어리** — 크기가 서로 같고, 아래나 오른쪽에 발문이 붙는다 | 글자 25px·폭 60px로 균일. 머리띠·배지·꼬리말은 흩어진다 |

선지 번호는 링 안의 숫자를 읽지 않고 **순서로 정한다** — 선지는 항상 순서대로 찍히므로
한 줄 5개 / 3+2 / 세로 1개씩이 모두 같게 처리된다. 문항 경계는 세로 간격으로 가른다
(같은 문항의 행 간격 55px vs 문항 사이 1000px 이상).

번호를 가려내는 규칙 넷 — 하나씩 실측에서 나왔다:

1. **종이 위에 있을 것.** 문제집은 "여기는 문제가 아니다"를 배경색으로 말한다. 개념 상자·유형
   머리띠 위의 것은 번호가 아니다 (종이색과 채도 차 0~2 vs 8~81). 기준은 흰색이 아니라
   그 페이지의 종이색이다 — 스캔은 종이가 누렇게 뜬다.
2. **크기가 서로 같을 것.** 한 쪽의 번호는 같은 자릿수·같은 서체다. 비교는 상자가 아니라
   글자 크기로 한다 — "[0001~0004]"를 반으로 자른 "[0001~"은 괄호가 키를 맞춰 상자가
   번호와 똑같지만 속 숫자는 한 급 작다.
3. **아래나 오른쪽에 발문이 있을 것.** 색 꼬리말 "(교사용)"은 크기도 좌단도 번호와 같아
   이것 말고는 걸러낼 방법이 없었다.
4. **문항 페이지라는 증거가 있을 것** — 번호가 3개 이상이거나 종이 위 선지 뭉치가 있을 것.
   개념 정리 쪽의 단원 표제("01·1", "04·5")가 여기서 걸린다.

단 좌단 정렬은 **거르는 데 쓰지 않는다.** 한 단 안에 번호 열이 둘인 조판이 있다 —
기본 문제 쪽은 짧은 주관식 37문항이 2×2 격자로 들어간다. 정렬선 하나만 남기면 그런 쪽에서
절반을 잃는다 (실측 37개 중 20개, 그래서 처음 인식률이 50%대였다).

**번호의 값(0109 같은)은 읽지 않는다.** 라이브 노트가 쓰는 것은 번호의 자리(배지를 띄울 곳)이고
선지 번호는 순서로 나오므로, 값 없이도 요구 1~4가 성립한다. 값이 필요해지면 그때 번호
크롭만 숫자 OCR에 넘기면 된다 — 그 자리는 비워 뒀다.

스캔본은 페이지마다 독립이라 통독하지 않는다. 쪽당 검출 28ms(렌더 별도),
문항 페이지 판정은 텍스트 경로와 같은 뜻이다 — 표지·개념정리 쪽은 "문항 없음"이 정답이다.

```sh
SCAN_PDF=~/Downloads/스캔본.pdf npx vitest run scan.real
```

**번호 인식은 손으로 확인한 정답과 맞춘다.** 페이지 그림을 직접 읽어 적은 15쪽(문항 96개)이
`scan.real.test.ts`의 `TRUTH`에 있다 — 표지·개념정리(문항 0)·유형·실력·서술형·마지막 쪽,
그리고 짧은 주관식 37개가 격자로 들어간 기본 문제 쪽까지. 쪽마다 문항 수·객관식 수·왼쪽 단
문항 수 세 값을 비교하고, 99% 미만이면 테스트가 깨진다.

2026-07-27 실측:
- 정답셋 15쪽 — **번호 인식 100%** (기준값 171 · 오차 0)
- 전수 180쪽 — 문항 1162 · 객관식 374 · 선지 5개 완비 373(99.7%) · **마킹 되읽기 1869/1869** ·
  쪽당 검출 32ms. 번호를 못 찾아 선지 위치로 대신한 문항은 **5개**(374 객관식 중 1.3%)
- 책의 마지막 번호가 1182이므로 전수 재현율은 대략 98%다. 정답셋 밖의 누락은 손으로 확인하지
  않았다 — 표본에서 100%라는 것과 전수에서 100%라는 것은 다른 말이다

합성 페이지 단위 테스트는 `scan.test.ts`에 있어 PDF 없이도 돈다.

한계: 번호에 색을 쓰지 않는 문제집에서는 번호를 못 찾는다 — 그때는 선지 뭉치 자체를
문항으로 세우고 배지를 ① 위에 붙인다. 기울어진 스캔·손글씨 원본은 다루지 않는다.

### 공통

에디터와 같은 부품(PageScroller · PdfCanvas · InkCanvas · PenToolbar)을 쓴다 —
필기 동작이 에디터와 달라지면 안 되기 때문이다. 다른 것은 판정 시점과 오버레이뿐이다.
필기는 `live:{파일명}` 키로 저장돼 같은 파일을 다시 열면 이어 쓴다. 문서 레코드를
만들지 않으므로 노트 목록에는 나오지 않는다.

마킹 되읽기는 실제 PDF로 잰다 (분할이 낸 hitbox ↔ 판정 사이의 계약):

```sh
PURI_BENCH_PDF=~/Downloads/문제집.pdf npx vitest run livemark
```

모든 객관식 문항의 모든 선지에 동그라미·빗금을 하나씩 쳐 보고 같은 번호가 돌아오는지
확인한다. 2026-07-26 기준 수능 260/260, 시중 문제집 752/752.
