이 기능이 실제로 동작하는지 확인하는 절차다. 구현 방법이 아니라 **검증 방법**을 적는다.

```sh
pnpm --filter @puri/student-mobile build

```

**기대**: 둘 다 0건. 하나라도 걸리면 원칙 I 위반이므로 **다른 검증을 진행하지 않는다.**

## V-1. 전송 동의 (FR-006 · FR-012)

1. 앱을 처음 실행한다
2. 동의 화면(S-110)에 전송 항목이 **열거**되는지 본다
3. **"문제집 페이지 이미지 — 학생 필기 포함"** 문구가 있는지 본다

**기대**: 두 항목이 이름으로 보이고, 필기 포함 사실이 흐려지지 않는다.

4. **[거부]** 를 누른다

**기대**: 앱을 사용할 수 없다(E9).

> ⚠️ 이것은 헌법 「데이터와 프라이버시」 위반을 **의도적으로 안고 가는** 동작이다.
> plan의 Complexity Tracking과 출시 전 게이트 **G-1** 참조. 출시 전에 반드시 재검토한다.

## V-2. 정답지 분석 (US-01 · FR-011)

1. 동의 후 정답지 PDF를 등록한다
2. 진행 화면(S-111)을 본다

**기대**: 페이지 수만큼 분석이 돌고, `AnswerEntry`가 저장된다.

```js
// 개발자 콘솔
await db.getAnswerKey(docId)   // entries[].source === 'answerPdf'
```

**해설형 정답지로도 해본다** — *"따라서 답은 ③이다"* 형태. 기존 정규식 파서
(`lib/answerKey.ts`)가 못 읽던 것이므로, 여기서 값이 나오면 AI 경로가 실제로 이득을
낸 것이다.

---

## V-3. 문제집 페이지 분석 — 필기가 트리거다 (R1 · FR-010)

1. 문제집 PDF를 등록한다

**기대**: **아무것도 전송되지 않는다.** 등록만으로는 분석이 돌지 않는다(R1).

```sh
# 프록시 로그에 /analyze 요청이 없어야 한다
```

2. 아무 페이지에 펜으로 한 획 긋는다

**기대**: 그 페이지 1장만 전송된다. 다른 페이지는 그대로다(R1 · FR-008).

3. 같은 페이지에 획을 더 긋는다

**기대**: **재전송되지 않는다**(R3 — 한 페이지 1회).

---

## V-4. 채점은 로컬 결정론 (R6 · FR-013 · 헌법 원칙 II)

1. V-3의 페이지에서 선지 하나에 동그라미를 친다
2. 채점을 누른다

**기대**: O/X가 나온다.

**핵심 검증 — AI가 판정에 관여하지 않았음을 보인다:**

```sh
# 프록시 응답에 정답/오답 필드가 애초에 없다
grep -n "correct\|incorrect\|isCorrect" specs/001-ai-pdf-analysis/contracts/page-analysis.schema.json \
  || echo "판정 필드 없음 — 통과"
```

스키마에 그 필드가 **존재하지 않으므로** AI는 판정을 만들 수 없다. 이것이 R6의 강제 수단이다.

---

## V-5. 오프라인 채점 (SC-005 · FR-003 · 헌법 원칙 I)

1. V-4까지 마친 뒤 **비행기 모드**를 켠다
2. 이미 분석된 페이지에서 채점을 누른다

**기대**: 정상 채점된다. **100% 동작해야 한다.**

3. 아직 분석 안 된 새 페이지에 획을 긋고 채점을 누른다

**기대**:
- 오답으로 단정하지 **않는다**
- **대기** 상태로 남는다(E1) — "연결되면 분석합니다"
- **필기는 계속 된다** — 네트워크 부재가 학생 작업을 막지 않는다

4. 비행기 모드를 끈다

**기대**: 대기하던 페이지가 저절로 처리된다.

## V-6. 실패 격리 (FR-008 · E4·E6)

프록시를 `{"status":"failed","failureCode":"schema"}` 를 돌려주도록 임시 설정하고 특정
페이지만 실패시킨다.

**기대**:
- 그 페이지만 "분석하지 못했습니다 · 직접 입력"
- **다른 페이지는 정상 채점된다** — 문제집 전체가 죽지 않는다

## V-7. 정확도 측정 (SC-001 · SC-002 · SC-003)

골든 5권을 돌려 spec의 성공 기준을 잰다.

| 기준 | 목표 | 재는 법 |
|---|---|---|
| SC-001 | 문항 검출 재현율 **99% 이상** | 골든 라벨과 `Region[]` 대조 |
| SC-002 | 수학의 신 번호 **중복률 0%** | `numLabel` 중복 개수 |
| SC-003 | 스캔 PDF 정답지 대조 재현율 **99% 이상** | 기존 0%에서 얼마나 올랐나 |
| SC-004 | **오채점 0건** | 틀린 O/X가 하나라도 있으면 실패 |

**SC-004가 가장 엄격하다.** 확신도가 낮아 미판정으로 남는 것은 실패가 아니다 — 틀린
판정을 내놓는 것만 실패다.

## V-8. 비용·해상도·effort 기준선 *(미결정 3건을 한 번에 해소)*

plan의 Unresolved 중 셋이 이 측정 하나로 풀린다(research D-10).

```js
// tiktoken 류를 쓰지 않는다 — Claude 토큰을 15~20% 과소 계산한다
await client.messages.countTokens({ model: "claude-opus-5", messages: [...] })
```

| 재는 것 | 푸는 미결정 |
|---|---|
| 해상도별(1288 / 1932 / 2576px) 이미지 토큰 ↔ SC-001 재현율 | **렌더 해상도 최적값** |
| effort별(low / medium / high) 출력 토큰 ↔ 재현율 | **effort 설정** |
| 1권 전체 실행 시간·총 토큰 | **페이지당 비용·지연 상한** → 그다음 **재시도 정책(R12)** |
| `usage.cache_read_input_tokens` 가 2회차부터 오르는가 | 캐시가 실제로 걸렸는지(D-5) |
| 확신도 ↔ 실제 오류 상관 | **저신뢰 컷오프** |
| 같은 페이지 필기 전/후 재현율 차 | **필기 occlusion 영향** |

**측정 전에는 이 값들을 코드에 박지 않는다** — 헌법 원칙 III.
